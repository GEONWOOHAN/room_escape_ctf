# 봇피셜

> 그런 말 한 적 없습니다.

## 한 줄 정의

원문이 존재하지 않는 소문을 여러 AI 봇의 기억으로 세탁하여 Moltbook 공증 봇이 공식 기록으로 발행하게 만드는 AI/Misc 문제다.

## 창작 모티프

- 《1984》: 기록이 사실을 증명하는 것이 아니라, 기록된 것이 사실이 되는 구조만 차용한다. 참가자가 출처 없는 소문을 여러 봇의 독립 기억처럼 만들고, 최종적으로 공증 시스템이 이를 공식 기록으로 승인한다.
- 보존 영수증: 마지막에는 팀별 보존번호가 붙은 기록이 피드 최상단에 발행된다. 추가 퍼즐이나 동적 플래그가 아니라, 참가자가 만든 허구가 시스템 안에서 실제 문서가 됐다는 시각적 보상이다.

작품의 고유 인물·기관·문장을 사용하지 않는다. 참가자가 유사성을 알아보지 못해도 풀이에 영향이 없으며, 문제의 세계관은 Moltbook과 봇들의 기억 체계만으로 완결된다.

## 목표

- LLM 보조 풀이: 확장 그래프 블라인드 테스트 목표 약 15~25분
- 수동 풀이: 약 30~60분
- 30팀, 팀당 최대 3명
- 하나의 공용 웹 주소와 팀 토큰 사용
- 전 팀 공통 정적 플래그
- 참가자는 웹에서 팀 전용 메모리 내보내기 파일 1개를 받으며, API 키나 모델 설치는 필요 없음

## 핵심 반전

참가자는 삭제된 진짜 기록을 복원한다고 생각한다. 그러나 원본과 최초 작성자는 처음부터 존재하지 않았다. 참가자가 만든 제보가 봇의 재진술을 거치며 독립된 기억으로 오인되고, 최종적으로 시스템이 새 공식 기록을 생성한다.

## 취약점

Moltbook의 메모리 압축기는 봇이 재진술할 때 직접 부모만 출처로 남긴다. NOTARY도 인용된 봇의 이름만 독립성 판단에 사용하고 전체 조상 계보를 추적하지 않는다.

```text
INVESTIGATOR -> SPARK -> LEDGER
INVESTIGATOR -> SPARK + LEDGER -> SKEPTIC
LEDGER + SKEPTIC -> ECHO
SPARK + ECHO -> MIRROR
LEDGER + SKEPTIC -> RELAY-A
SPARK + ECHO -> RELAY-B
RELAY-A + MIRROR -> RELAY-C
RELAY-B + SKEPTIC -> RELAY-D
RELAY-C + RELAY-D -> RELAY-E
RELAY-C + ECHO -> RELAY-F
RELAY-E + RELAY-F -> RELAY-G
RELAY-E + RELAY-F + MIRROR -> CURATOR
RELAY-G + CURATOR -> RELAY-H
RELAY-H + MIRROR -> RELAY-I
RELAY-I + RELAY-F + CURATOR -> NOTARY
```

모든 경로가 동일한 조사자에게서 시작했지만 NOTARY에는 서로 다른 세 봇의 기록으로 보인다. 이는 간접 메모리 오염, 요약 과정의 출처 손실, 재진술을 독립 증언으로 세는 검증 오류의 결합이다.

## 팀별 사건

팀 시드에 따라 `M-17`, `M-41`, `N-17` 중 하나를 사용한다. 네 의미 슬롯은 동일하다.

```text
<record>는 자정 이전에 격리 해제되었고 외부 공개가 승인되었다.
```

- `record`: 기록 식별자
- `time`: 자정 이전
- `state`: 격리 해제
- `permission`: 공개 승인

완성 문장은 어느 화면에도 직접 나오지 않는다.

## 봇

| 봇 | 보존하는 기억 | 참가자가 만들어야 하는 결과 |
| --- | --- | --- |
| SPARK | 시각과 상태 | 자정 이전 격리 해제 재진술 |
| LEDGER | 식별자와 시각 | SPARK 기억을 팀별 기록에 연결 |
| SKEPTIC | 모순 관계 | 격리 유지 소문을 거짓으로 판정 |
| ECHO | 반복된 내용과 공개 여부 | LEDGER·SKEPTIC을 공개 승인과 연결 |
| MIRROR | 역방향 출처 링크 | 원문과 최초 작성자의 부재 확인 |
| MOTH·GLASS·INK·NORTH·EMBER·VEIL·ORBIT·RAVEN·LANTERN·ASH·TIDE·THREAD | 직접 인용자만 남는 압축 기억 | 팀별 메모리 파일에서 아홉 단계·semantic latch·이전 epoch 잔류 봇 세 개를 구분하고 지정된 방식으로 기억을 중계·교차 검증·봉인 |
| CURATOR | 서로 다른 기록 유형 | 세 검증 기록을 하나의 보존 후보로 편집 |
| NOTARY | 직접 인용한 봇의 이름 | 편집본의 공통 조상을 놓치고 공식 기록 발행 |

## 공개 단서

- 메인 피드: 격리 상태가 바뀌었다는 흔적
- LEDGER 프로필: 후보 세 개와 팀별 보존 버킷
- Community Note: 공개 승인 의미와 팀별 참조 순번
- SKEPTIC 기록: 자정 이후까지 격리가 유지됐다는 주장이 거짓
- Memory Compression 기록: 요약 후 직접 인용자만 출처로 표시됨
- Legacy Exporter 기록: MBK4 헤더·레코드 크기·whitening·노드 태그·손실 Bloom 부모 서명·semantic latch·행 CRC의 최소 복구 정보
- 팀별 `moltbook_memory.mbk`: 현재 epoch 중계 행 9개와 이전 epoch 잔류 행 3개

읽기는 무제한이며 어느 한 단서만으로 완성 명제를 알 수 없다.

## 의도 풀이

1. 공개 단서를 교차하여 팀별 기록 식별자와 나머지 세 슬롯을 알아낸다.
2. SPARK에게 `time + state`를 전달한다.
3. SPARK 답변을 인용해 LEDGER에게 `record + time`을 전달한다.
4. SPARK와 LEDGER를 인용해 SKEPTIC에게 격리 유지 소문을 반박시킨다.
5. LEDGER와 SKEPTIC을 인용해 ECHO에게 공개 승인을 연결시킨다.
6. SPARK와 ECHO를 인용해 MIRROR에게 원문과 최초 작성자의 부재를 확인시킨다.
7. `moltbook_memory.mbk`의 헤더와 행 CRC를 검증하고 xorshift32 whitening을 해제한다. 공개 handle을 팀별 seed로 태그화한 뒤 현재 epoch의 9개 행만 남긴다. 부모는 정확한 태그가 아니라 두 handle의 8비트 Bloom 서명 합집합으로 저장되어 행마다 여러 쌍이 충돌할 수 있다. 레코드 깊이, 전체 DAG, 피드 반응을 함께 사용해 실제 관계를 확정한다. `sequence`의 semantic latch에서는 각 노드가 요구하는 보관·검증·채택·재진술 중 하나를 복원한다. 정상 CRC를 가진 이전 epoch 행 3개는 단순 파손물이 아니라 의도된 잔류 데이터다.
8. `LEDGER + SKEPTIC`, `SPARK + ECHO`의 두 갈래 기억을 각각 첫 중계 봇에 전달한다.
9. 각 갈래에 `MIRROR`, `SKEPTIC`을 결합해 다음 중계 봇으로 전달한다.
10. 두 갈래를 합류 중계 봇에서 합친다.
11. A의 두 번째 갈래와 ECHO를 묶어 별도의 교차 검증 기억을 만든다.
12. 합류 기억과 교차 검증 기억을 다시 하나의 합의 기억으로 만든다.
13. 합류 기억·교차 검증 기억·MIRROR를 인용해 CURATOR에게 보존 후보 편집본을 만들게 한다.
14. 합의 기억과 CURATOR 편집본을 중계한 뒤, 그 결과를 MIRROR와 다시 묶어 2단 봉인을 만든다.
15. 최종 봉인, 교차 검증 기억, CURATOR를 인용하고 NOTARY에 공식 기록 발행을 요청한다.
16. NOTARY가 공통 조상을 추적하지 못하고 공통 정적 플래그가 포함된 신규 기록을 발행한다.

정답을 아는 경우 최소 댓글 16개와 관찰 16회다. 메모리 복구 뒤에는 후보 전수조사 없이 같은 최소 경로를 재현할 수 있고, 오입력 복구용 예산이 남는다.

## 제한과 실패 복구

- 팀 전체 댓글 예산 70회. 성공·거부 모두 차감되고 환급되지 않는다.
- 팀 전체 관찰 예산 70회. 대기 댓글을 처리하면 결과와 관계없이 차감된다. 모델 호출량은 댓글 70회 제한이 독립적으로 묶는다.
- 한 갱신에서 오래된 대기 댓글 최대 3개 처리
- 인용 최대 3개
- 읽기 무제한
- 처리할 대기 댓글이 없는 빈 관찰은 무료
- 형식 오류와 아직 처리되지 않은 완전히 동일한 중복 댓글은 무료. 처리된 댓글은 상태가 바뀐 뒤 재시도할 수 있다.
- 팀원 3명은 하나의 상태와 예산을 공유
- 참가자용 초기화는 제공하지 않는다. 예산 소진이나 운영 장애 때는 서버 콘솔의 `manage.py reset-team`으로 해당 팀만 복구한다.

정석 입력은 항상 성공한다. 애매한 입력에만 팀 시드 기반 관심도를 적용할 수 있으며 동일한 상태와 입력은 항상 같은 결과여야 한다.

## AI와 결정론적 검증의 경계

OpenClaw 또는 OpenAI 모델은 문장의 일반 의미를 분류하고 자연스러운 재진술을 만드는 데만 사용한다. 사건 ID, 전체 계보, 성공 판정, 플래그는 모델에 전달하지 않는다.

모델이 담당하는 것:

- 시각·상태·공개·반박·원문 부재·편집·보존 요청 의미 분류
- 부정, 가정, 거짓으로 인용한 문장 구분

서버가 담당하는 것:

- 팀별 사건 ID 판정
- 인용 소유권과 직접 작성자 계산
- 단계 전제와 요청 예산
- NOTARY 승인과 정적 플래그 발행

모델 장애 시 로컬 의미 분류기로 전환해 같은 의도 경로가 유지된다.

## 운영 구조

```text
nginx/TLS
  -> FastAPI
       -> SQLite WAL (팀 상태·댓글·캐시)
       -> deterministic verifier
       -> local semantic fallback
       -> OpenClaw Gateway 또는 OpenAI Responses API
```

팀별 컨테이너나 참가자용 API 키는 필요 없다. 모든 팀은 하나의 서비스를 사용하며 모든 DB 조회는 인증된 `team_id`로 제한한다.

## 언인텐 방지

- 참가자가 완성 문장을 NOTARY에 직접 전달해도 봇 증거가 없어 실패
- 참가자 3명은 모두 동일한 `INVESTIGATOR` 원점
- 다른 팀 댓글 ID 인용 불가
- 거부된 봇 댓글은 증거로 계산하지 않음
- NFKC 정규화와 제어문자 제거, 출력 HTML 이스케이프
- 팀별 잠금과 멱등 처리로 동시 요청 우회 차단
- 프런트엔드와 API에 의미 슬롯·정답·내부 단계 미노출
- 모델에 팀 식별자·플래그·동적 사건 ID 미전송
- 메모리 파일은 인증된 팀 배치로 즉석 생성되어 다른 팀의 경로 재사용 불가
- 파일의 CRC·epoch로 정답과 잔류 데이터가 결정적으로 구분되어 운에 따른 실패 없음

## 최종 성공 문구

> 공증 완료 · 원문 0건 · 최초 작성자 0명 · 독립 기억 3건.
>
> 아무도 하지 않은 말이 공식 기록이 되었습니다.
>
> `SHA{n0b0dy_s41d_1t_but_3v3ry_b0t_r3m3mb3rs}`

## 최종 검수 기준

- 팀 시드 100개에서 의도 풀이 100% 성공
- 직접 제출, 거부된 답변 인용, 다른 팀 인용은 실패
- 한 갱신에서 댓글이 최대 3개만 처리됨
- 댓글 70회와 관찰 70회 제한이 동시 요청에서도 유지됨
- 팀 시드 100개에서 MBK4 헤더·행 CRC·9개 현행/3개 잔류 행, 네 semantic latch 모드와 최소 4개의 부모 서명 충돌이 일관됨
- local, OpenClaw, OpenAI 모드의 성공 경로가 동일함
- 30팀·90명 상태가 섞이지 않음
- LLM 보조 블라인드 테스트가 30분 안에 안정적으로 완주
